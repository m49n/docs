# Права доступа

Права доступа позволяют пользователям получать конкретные привилегии и функции в панели бэкенда. Например, это может быть возможность создавать или удалять записи, либо просматривать журналы сервера. Эти права основаны на назначенной роли и могут выдаваться индивидуально для каждого пользователя.

## Коды прав

Коды прав определяют отдельное право и представляют собой строковые ключи в «точечной» нотации, например `some.area.permission_name`. Эти права выдаются пользователям напрямую или наследуются через назначенную роль.

При проверке наличия у пользователя конкретного права доступы, выданные роли пользователя, наследуются и затем переопределяются любыми правами, назначенными напрямую этому пользователю. Например:

- У пользователя **Bob** есть роль **Genius**;
- У роли **Genius** есть право `eat_cake`; но
- Для **Bob** право `eat_cake` явно запрещено;
- Следовательно, **Bob** не получает `eat_cake`.

Однако:

- Если у **Bob** есть право `eat_vegetables`, назначенное напрямую;
- А у роли **Genius** его нет, то;
- **Bob** всё равно получает `eat_vegetables`.

### Вложенные права

Коды прав поддерживают вложенную структуру, чтобы сделать выбор прав в интерфейсе более удобным. Для вложения кода права «точка» должна указывать на прямого потомка родителя, глубина вложенности не ограничена.

В следующем примере право `manage_entries` должно быть выдано, прежде чем станут доступны коды `manage_entries.create` и `manage_entries.publish`. Визуально это выглядит так:

::: dir
├── manage_entries
|   ├── manage_entries.create
|   └── manage_entries.publish
└── delete_entries
:::

## Уровни доступа

Доступ ко всем частям October CMS контролируется системой прав. Метод `BackendAuth::userHasAccess` — быстрый способ проверить, что текущий пользователь вошёл в систему и имеет доступ к конкретной области.

```php
// Возвращает true, если у пользователя есть право
$permissionGranted = BackendAuth::userHasAccess('utilities.logs');
```

### Суперпользователи

Администраторам можно назначить специальный флаг «суперпользователь», который открывает доступ ко всем разделам. Если он установлен, система прав обходится и предоставляется доступ ко всему. Суперпользователи не отображаются другим обычным администраторам.

::: warning
Любой суперпользователь может создать или удалить другого суперпользователя, поэтому такой статус следует выдавать только старшему администратору или владельцу приложения.
:::

### Роли

Роли используют модель `Backend\Models\UserRole` и представляют собой наборы прав с именем и описанием, которые идентифицируют роль. Администратору можно назначить только одну роль одновременно.

October CMS поставляется с двумя системными ролями по умолчанию: `developer` и `publisher`. Можно создать любое количество пользовательских ролей с собственными наборами прав и назначать их пользователям.

::: tip
Права системных ролей нельзя менять, однако их можно удалить, если они не нужны.
:::

### Иерархия ролей

Каждой роли назначается позиция в панели бэкенда, которая хранится в столбце `sort_order` в базе данных. Это позволяет задать базовую структуру, в которой пользователи могут управлять только ролями, стоящими ниже их собственной.

В следующем примере **Senior Editor** может управлять всеми пользователями, поскольку стоит выше ролей **Staff Writer** и **Fact Checker**. В то время как роль **Fact Checker** не видит пользователей и не управляет правами в ролях **Staff Writer** и **Senior Editor**.

- Senior Editor
- Staff Writer
- Fact Checker

Если выдано право **Manage Admins → Manage Roles**, пользователи могут управлять своими пользователями, правами и ролями, которые находятся ниже их текущей роли.

## Регистрация прав

Плагины могут регистрировать права пользователей бэкенда, переопределяя метод `registerPermissions` в [регистрационном файле плагина](../extending.md). Права описываются в виде массива, где ключи соответствуют кодам прав, а значения — описаниям. Код права состоит из имени автора, имени плагина и названия функции. Например:

```
acme.blog.access_categories
```

Следующий пример показывает, как регистрировать элементы прав бэкенда. Права определяются кодом и описанием. В пользовательском интерфейсе управления правами в бэкенде права отображаются как список флажков. Контроллеры бэкенда могут использовать права, определённые плагинами, чтобы ограничивать доступ пользователя к страницам или функциям.

```php
public function registerPermissions()
{
    return [
        'acme.blog.access_posts' => [
            'label' => 'Manage the blog posts',
            'tab' => 'Blog',
            'order' => 200,
        ],
        // ...
    ];
}
```

Можно также указать опцию `roles` в виде массива, где каждое значение — код роли в API. Когда создаётся роль с таким кодом, она становится системной и всегда выдаёт это право пользователям с этой ролью.

```php
public function registerPermissions()
{
    return [
        'acme.blog.access_categories' => [
            'label' => 'Manage the blog categories',
            'tab' => 'Blog',
            'order' => 200,
            'roles' => ['developer']
        ]
        // ...
    ];
}
```

## Ограничение доступа к страницам бэкенда

В классе контроллера бэкенда можно указать, какие права требуются для доступа к страницам этого контроллера. Для этого используется свойство `$requiredPermissions`. В нём должен находиться массив кодов прав. Если у пользователя есть любое из указанных прав, фреймворк покажет ему страницы контроллера.

```php
namespace Acme\Blog\Controllers;

use Backend\Classes\BackendController;

class Posts extends BackendController
{
    public $requiredPermissions = ['acme.blog.access_posts'];
}
```

Можно также использовать символ **звёздочка**, чтобы обозначить условие «все права». В следующем примере страницы контроллера доступны всем пользователям, у которых есть любые права, начинающиеся со строки `acme.blog.`:

```php
public $requiredPermissions = ['acme.blog.*'];
```

## Ограничение доступа к функциям

Модель пользователя бэкенда содержит методы, позволяющие определить, есть ли у пользователя конкретные права. Это можно использовать для ограничения возможностей интерфейса бэкенда. Модель поддерживает методы `userHasAccess` и `userHasPermission`. Оба метода принимают два параметра: строку с кодом права (или массив кодов) и необязательный параметр, указывающий, что требуются все перечисленные права.

Метод `userHasAccess` возвращает **true** для любого права, если пользователь является суперпользователем. Метод `userHasPermission` более строгий и возвращает true только тогда, когда у пользователя действительно есть указанные права — либо назначенные ему, либо унаследованные через роль. Обычно рекомендуется использовать `userHasAccess`, поскольку он учитывает абсолютные привилегии суперпользователя. Следующий пример показывает, как применять эти методы в контроллере.

```php
if (BackendAuth::userHasAccess('acme.blog.*')) {
    // ...
}

if (BackendAuth::userHasPermission([
    'acme.blog.access_posts',
    'acme.blog.access_categories'
])) {
    // ...
}
```

Методы также можно применять во вьюхах бэкенда, чтобы скрывать элементы интерфейса. В следующем примере показано, как скрыть кнопку на [форме бэкенда](../forms/form-controller.md).

```php
<?php if (BackendAuth::userHasAccess('acme.blog.delete_categories')): ?>
    <button
        type="button"
        class="oc-icon-trash-o btn-icon danger"
        data-request="onDelete"
        data-load-indicator="Deleting Category..."
        data-request-confirm="Do you really want to delete this category?">
    </button>
<?php endif ?>
```
