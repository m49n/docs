# Приложение

Контейнер инверсии управления (IoC) — инструмент для управления зависимостями классов. Внедрение зависимостей — способ устранить жёстко заданные зависимости классов. Вместо этого зависимости внедряются во время выполнения, что обеспечивает большую гибкость, поскольку реализации зависимостей можно легко заменить.

#### Связывание с контейнером

Есть два способа, которыми контейнер IoC может разрешать зависимости: через колбэки `Closure` или автоматически. Сначала рассмотрим колбэки `Closure`. Сначала «тип» можно связать с контейнером.

```php
App::bind('foo', function($app) {
    return new FooBar;
});
```

#### Разрешение из контейнера

```php
$value = App::make('foo');
```

Когда вызывается метод `App::make`, выполняется колбэк `Closure`, и возвращается его результат.

#### Связывание «разделяемого» типа с контейнером

Иногда требуется связать с контейнером нечто, что должно быть разрешено только один раз, а при последующих обращениях к контейнеру должен возвращаться один и тот же экземпляр:

```php
App::singleton('foo', function() {
    return new FooBar;
});
```

#### Связывание существующего экземпляра с контейнером

Можно также связать существующий объект с контейнером с помощью метода `instance`:

```php
$foo = new Foo;

App::instance('foo', $foo);
```

#### Связывание интерфейса с реализацией

В некоторых случаях класс может зависеть от реализации интерфейса, а не от «конкретного типа». В таком случае нужно использовать метод `App::bind`, чтобы указать контейнеру, какую реализацию интерфейса внедрять:

```php
App::bind('UserRepositoryInterface', 'DbUserRepository');
```

Рассмотрим следующий код:

```php
$users = App::make('UserRepositoryInterface');
```

Поскольку мы связали `UserRepositoryInterface` с конкретным типом, при создании этого контроллера в него автоматически будет внедрён `DbUserRepository`.

### Где регистрировать связывания

Связывания IoC, как и [обработчики событий](./event.md), обычно относятся к категории «bootstrap-кода». Другими словами, они подготавливают приложение к обработке запросов и обычно должны выполняться до того, как будет вызван маршрут или контроллер. Чаще всего их размещают в методе `boot` [регистрационного файла плагина](../extending.md). Также плагин может предоставить файл **init.php** в каталоге плагина, который можно использовать для логики регистрации в IoC.

## Провайдеры служб

Провайдеры служб — отличный способ создавать библиотеки и группировать связанные регистрации IoC в одном месте. Внутри провайдера служб можно зарегистрировать собственный драйвер аутентификации, зарегистрировать классы репозиториев приложения в контейнере IoC или даже настроить собственную команду Artisan.

Фактически [регистрационные файлы плагинов](../system/plugins.md) наследуют провайдеры служб, и большинство ключевых компонентов включают провайдеры служб. Все зарегистрированные провайдеры служб приложения перечислены в массиве `providers` файла конфигурации `config/app.php`.

#### Определение провайдера служб

Чтобы создать провайдера служб, расширьте класс `October\Rain\Support\ServiceProvider` и определите метод `register`:

```php
use October\Rain\Support\ServiceProvider;

class FooServiceProvider extends ServiceProvider
{
    public function register()
    {
        $this->app->bind('foo', function() {
            return new Foo;
        });
    }
}
```

Обратите внимание, что в методе `register` контейнер IoC приложения доступен через свойство `$this->app`. После создания провайдера и готовности зарегистрировать его в приложении просто добавьте его в массив `providers` файла конфигурации `app`.

#### Регистрация провайдера служб во время выполнения

Также можно зарегистрировать провайдера служб во время выполнения с помощью метода `App::register`.

```php
App::register('FooServiceProvider');
```

## События приложения

#### События запроса

Можно зарегистрировать специальные события до маршрутизации запроса с помощью методов `before` и `after`.

```php
App::before(function ($request) {
    // Код, выполняемый до маршрутизации запроса
});

App::after(function ($request) {
    // Код, выполняемый после маршрутизации запроса
});
```

#### События контейнера

Контейнер служб инициирует событие каждый раз при разрешении объекта. Можно подписаться на это событие методом `resolving`.

```php
App::resolving(function ($object, $app) {
    // Вызывается, когда контейнер разрешает объект любого типа...
});

App::resolving('foo', function ($fooBar, $app) {
    // Вызывается, когда контейнер разрешает объекты с подсказкой «foo»...
});

App::resolving('Acme\Blog\Classes\FooBar', function ($fooBar, $app) {
    // Вызывается, когда контейнер разрешает объекты типа «FooBar»...
});
```

Как видно, объект, который разрешается, передаётся в колбэк, что позволяет задать дополнительные свойства объекта до передачи потребителю.

## Хелперы приложения

#### Определение окружения приложения

Метод `environment` позволяет узнать окружение приложения, определённое [конфигурацией окружений](../../setup/configuration.md).

```php
// production
App::environment();
```

#### Определение контекста выполнения

Можно узнать, выполняется ли текущий запрос в административной области бэкенда, с помощью метода `runningInBackend`.

```php
App::runningInBackend();
```

Также можно использовать метод `runningInConsole`, чтобы проверить, выполняется ли код внутри [интерфейса командной строки](../console-commands.md):

```php
App::runningInConsole();
```
