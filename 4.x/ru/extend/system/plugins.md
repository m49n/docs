# Плагины

::: aside
Плагин идентифицируется уникальным кодом. Например, плагин `Acme.Blog` хранится в каталоге **plugins/acme/blog**.
:::

В этой статье описаны плагины и их регистрационные функции. В процессе регистрации плагин объявляет свои возможности — компоненты CMS, навигацию бэкенда, страницы и другое. Ниже перечислены примеры того, что может делать плагин.

1. Создавать структуры таблиц и загружать данные.
1. Определять [компоненты CMS](../cms-components.md).
1. Определять [разрешения пользователей](../backend/permissions.md).
1. Добавлять [страницы настроек](../settings/settings.md), [элементы навигации](../backend/navigation.md), [списки](../lists/list-controller.md) и [формы](../forms/form-controller.md).
1. Изменять [функциональность ядра или других плагинов](../extending.md).
1. Предоставлять классы, [контроллеры бэкенда](../system/controllers.md), представления, ресурсы и другие файлы.

### Структура каталогов

Плагины располагаются в каталоге **plugins** директории приложения. Пример структуры каталога плагина:

::: dir
├── `plugins`
|   └── acme  _← Имя автора_
|       └── blog  _← Имя плагина_
|           ├── classes
|           ├── components
|           ├── controllers
|           ├── models
|           ├── updates
|           └── Plugin.php  _← Регистрационный файл_
:::

Не все каталоги обязательны. Единственный необходимый файл — **Plugin.php**, описанный ниже. Если плагин предоставляет только один компонент, структура может быть значительно проще:

::: dir
├── plugins
|   └── acme
|       └── blog
|           ├── `components`
|           └── Plugin.php
:::

### Пространства имён плагинов

Пространство имён плагина критически важно, особенно если плагин публикуется на [маркетплейсе October CMS](https://octobercms.com/plugins). При регистрации в качестве автора требуется указать авторский код — его следует использовать как корневое пространство имён для всех плагинов. Код автора задаётся один раз при регистрации. По умолчанию маркетплейс предлагает код, составленный из имени и фамилии автора, например JohnSmith. После регистрации изменить код нельзя. Все пространства имён плагинов должны находиться под корневым пространством, например `JohnSmith\Blog`.

## Регистрационный файл

Команда `create:plugin` создаёт каталог плагина и базовые файлы. Первый аргумент задаёт автора и имя плагина.

```bash
php artisan create:plugin Acme.Blog
```

Файл **Plugin.php**, называемый регистрационным файлом плагина, — это скрипт инициализации, который объявляет основные возможности и информацию о плагине. Регистрационный файл может содержать следующее:

1. Информацию о плагине, его название и автора.
1. Методы регистрации для расширения CMS.

Регистрационный скрипт должен использовать пространство имён плагина. В нём определяется класс `Plugin`, наследующий `System\Classes\PluginBase`. Единственный обязательный метод — `pluginDetails`. Пример регистрационного файла:

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    public function pluginDetails()
    {
        return [
            'name' => 'Blog Plugin',
            'description' => 'Provides some really cool blog features.',
            'author' => 'ACME Corporation',
            'icon' => 'icon-leaf'
        ];
    }

    public function registerComponents()
    {
        return [
            \Acme\Blog\Components\Post::class => 'blogPost'
        ];
    }
}
```

### Основные сведения о плагине

Метод `pluginDetails` обязателен и должен возвращать массив со следующими ключами:

Ключ | Описание
------------- | -------------
**name** | Название плагина (обязательно).
**description** | Описание плагина (обязательно).
**author** | Имя автора плагина (обязательно).
**icon** | Имя значка плагина. Полный список доступен в [справочнике по иконкам](../../element/available-icons.md). Подходят любые имена из этого набора, например **icon-glass**, **icon-music** (необязательно).
**iconSvg** | SVG-значок вместо стандартного. SVG должен быть прямоугольным и может содержать цвета (необязательно).
**homepage** | Ссылка на сайт автора (необязательно).
**hint** | Сокращённый код для [маршрутов URL контроллеров](./controllers.md) в админ-панели (необязательно).

## Загрузка и инициализация

Регистрационный файл может содержать методы `boot` и `register`. В них можно выполнять любые действия: регистрировать маршруты, подписываться на события и т. д.

Метод `register` вызывается сразу при регистрации плагина. Метод `boot` вызывается непосредственно перед обработкой запроса. Если логика зависит от другого плагина, используйте метод `boot`. Например, внутри `boot` можно расширять модели.

```php
public function boot()
{
    User::extend(function($model) {
        $model->hasOne['author'] = \Acme\Blog\Models\Author::class;
    });
}
```

::: tip
Метод `boot` необязателен: его отсутствие положительно влияет на производительность. Кроме того, только метод `boot` поддерживает внедрение зависимостей через контейнер приложений.
:::

Плагин может также содержать файл **init.php** с пользовательской логикой инициализации. Пример содержимого:

```php
App::before({
    // Logic when the request starts, after routes are registered
});

App::after({
    // Logic the request has finished, after the response is sent
});
```

## Определение зависимостей

Плагин может зависеть от других плагинов, указав свойство `$require` в регистрационном файле. В свойстве перечисляются имена обязательных плагинов. Например, плагин, зависящий от **Acme.User**, описывается так:

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    /**
     * @var array Требуемые плагины
     */
    public $require = ['Acme.User'];

    // ...
}
```

Определённые зависимости влияют на работу плагина и порядок применения обновлений. При установке система попытается автоматически установить зависимости, однако если плагин обнаружен без обязательных зависимостей, он будет отключён для предотвращения ошибок.

Зависимости могут быть сложными, но важно избегать циклических ссылок. Граф зависимостей должен оставаться направленным; циклическая зависимость считается ошибкой проектирования.

## История версий

Практикой хорошего тона является ведение журнала изменений, в котором фиксируются обновления кода. Помимо описания изменений, этот процесс позволяет выполнять [миграции и загрузчики данных](../database/structure.md) в нужном порядке.

Журнал изменений хранится в YAML-файле `version.yaml` в каталоге **updates** плагина наряду с файлами миграций и загрузчиков данных. Пример структуры каталога обновлений:

::: dir
├── plugins
|   └── author
|       └── myplugin
|           ├── `updates`
|           |   ├── `version.yaml`  _← Файл версий_
|           |   ├── create_tables.php  _← Скрипт БД_
|           |   ├── seed_the_database.php
|           |   └── create_another_table.php
|           └── Plugin.php
:::

### Зависимости плагинов

Обновления применяются в определённом порядке в соответствии с зависимостями, указанными в регистрационном файле. Плагины, зависящие от других, не обновляются, пока не обновлены их зависимости.

```php
namespace Acme\Blog;

class Plugin extends \System\Classes\PluginBase
{
    public $require = ['Acme.User'];
}
```

В этом примере плагин **Acme.Blog** не будет обновлён, пока полностью не обновится **Acme.User**.

## Файл версий плагина

Файл **version.yaml** содержит комментарии к версиям и указывает скрипты базы данных в нужном порядке. Подробнее о файлах миграций см. статью [Структура базы данных](../database/structure.md). Этот файл обязателен, если планируется публикация плагина на [маркетплейсе](https://octobercms.com/help/site/marketplace). Пример файла версий:

```yaml
v1.0.1: First version
v1.0.2: Second version
v1.0.3:
    - Update with a migration and seed
    - create_tables.php
    - seed_the_database.php
v2.0.0: Important update
v2.0.1: Latest version
```

::: tip
В файле `version.yaml` первая строка всегда должна описывать изменения, а последующие строки — содержать скрипты обновления. Для более подробных заметок используйте отдельный файл changelog.
:::

Как видно выше, ключом служит номер версии, за которым следует комментарий — строка или массив строк. Если обновление связано с миграциями или загрузчиками данных, строки с именами скриптов можно располагать в любом порядке. Пример комментария без связанных файлов:

```yaml
v1.0.1: A single comment that uses no update scripts.
```

### Важные обновления

Иногда плагин добавляет возможности, несовместимые с существующими установками. Чтобы изменения не развёртывались автоматически, увеличьте **major**-часть версии (`major.minor.patch`). Пример комментария для важного обновления:

```yaml
v2.1.0: This is an important update from v1 that contains breaking changes.
```

При выпуске версии `v2` после `v1` такие изменения не устанавливаются в рамках обычного обновления. Пользователь должен переустановить плагин, чтобы получить последнюю версию через Composer.

### Файлы миграций и загрузчиков данных

Как упоминалось выше, обновления также определяют, когда применять [файлы миграций и загрузчиков данных](../database/structure.md). Строка обновления с комментарием и файлами выглядит так:

```yaml
v1.1.1:
    - This update will execute the two scripts below.
    - some_upgrade_file.php
    - some_seeding_file.php
```

Имя файла обновления следует записывать в *snake_case*, а соответствующий класс — в *CamelCase*. Для файла **some_upgrade_file.php** класс будет `SomeUpgradeFile`.

```php
<?php namespace Acme\Blog\Updates;

use Schema;
use October\Rain\Database\Updates\Migration;

/**
 * some_upgrade_file.php
 */
class SomeUpgradeFile extends Migration
{
    ///
}
```
